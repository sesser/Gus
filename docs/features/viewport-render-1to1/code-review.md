## Verdict

Not ready to merge. The renderer (`LiveRegionRenderer`) is correct and its tests have teeth, but the region-frame integration has four blocking defects at 100%: the photo's tile covers the sharpening and fringe maps, a raw white balance, profile or noise reduction drag freezes on a stale tile, the mask overlay does not follow the selected mask, and Highlights or Exposure crossing zero on a raw is soft for the whole drag. Nothing here changes saved renders, exports or cached previews.

## Questions

- **Requirements (RI2, product manager or owner).** The texture check is dimension-only (`maximumTextureDimension`, 16384). A photo of 16384 × 12288 would hold about 1.6 GB, and `status.md` stopped its 96 MP run after ten minutes. A5 says a problem on larger photos comes back as a requirements issue, and RI2 has no ruling. Should covered zooms have a byte cap, with soft frames beyond it?
- **Design (for the designer's review).** Whether the mask handles still draw over the tile: `tileLayer` is a sublayer added directly to a layer-backed view (`LoupeView.swift:1159`), and AppKit manages that view's sublayer order. It can only be checked on screen.

## Checked and fine

- **Renderer.** Actor isolation; `render` never runs on the main actor; `prepare` decodes in a detached task and drops superseded results; no `nonisolated(unsafe)`. `Base: @unchecked Sendable` has a written reason that holds (`waitUntilCompleted` before any read). Frames are `deferred: false` BGRA8 in the display's color space.
- **R12's tolerance and tests.** Derived from the formats (C13 only tightens it). Mutations of a scratch copy of `LiveRegionRenderer.swift`, each run with `swift test --filter LiveRegionRendererTests`: unmodified, 8 of 8 tests pass; with the region shifted one pixel vertically, shifted one pixel horizontally, the texture not flipped, or the master softened by a 0.7 sigma blur, all four comparison tests fail (7 issues each, across the center, corner, cropped, raw, one-pixel and Show Original cases).
- **Stale frames.** The render loop is serial, so frames land in order; `session === self.session` and `loupeViewport != nil` drop late ones after a change of photo or zoom. `finishSession` clears the tile's frame and the renderer.
- **Texture memory.** Freed by `purge` on leaving covered zooms and by dropping the renderer on a new photo. Allocation failure and too-large photos fall back to soft frames, never blank, with no crash path.
- **R1 below 100%.** The diff doesn't change Fit: `loupeViewport` is nil, every new branch is skipped, filtering at magnification below 1 is unchanged. Consistent with `status.md`'s Masking measurements.
- **R13, R14, AC12.** Seeds come only from whole frames (`frame`), never `regionFrame` (quality exception: C9). No pipeline bump, no goldens, no change to `PreviewCacheKey`, `RenderEngine` or export paths. `LiveRenderSession.withOverlay` is a straight extraction.
- **R9.** Histogram only from whole frames; region frames and pans never touch it.
- **R11, undo.** `change`/`commit`/`apply` unchanged; one save per gesture. `adjust scrub` runs inside `adjust`, which is in `DebugScript`'s `changing` set; `zoomstep` and `print` change no photo.
- **Strings and branding.** Two hints and the widened comment match design §1 and §5; old keys removed; no new UI strings; `LocalizationTests` and `BrandingTests` pass. `Package.swift` unchanged, no new dependency, no clean-room concern.

**The test failure seen once (question 2).** I can find no way this branch makes those renders non-deterministic, and I could not rule out GPU load making an existing race more likely.

What I checked and ran:

- Those tests' code paths are untouched on this branch: `AdjustmentRenderer.swift`, `Sources/PhotoCore/Preview`, `Sources/PhotoFixtures`, `SharpeningMapTests.swift`, `SharpenTests.swift` and `EffectsTests.swift` have an empty diff against `dfa0d5c`.
- No shared context: `SharpeningMapTests` renders through its own `static floatContext`, `EffectsRenderingTests` through an `engine` made per test, and `LiveRegionRendererTests` through its own `RenderEngine(contextCount: 1, name: "region-test")` or a fresh `PreviewGenerator()`. What the process shares is the GPU and the Metal device. Scene and grain are seeded or fixed (`SharpenTests.scene`, `CIRandomGenerator`).
- Filtered runs of those two suites: 20 on the branch alone, 20 on the branch with `LiveRegionRendererTests` looping in a second process, 20 on `dfa0d5c` while other GPU work ran. All passed. A separate scratch probe of 400 concurrent renders through `floatContext` and 60 of the grain graph showed no difference from the serial result.
- Full suite on the branch at `e6dd936`: 13 runs in the working tree, 12 passed. The one failure is `SharpeningMapTests`, lines 188 and 191, the `input` render, in a run with a second process loading the GPU; the suite took 30 s there against 0.7 s alone. A scratch copy under the same load, 7 runs: 6 passed, 1 failed with a different test, `cancellingTheLastWaiterCancelsTheJob` (`PreviewTests.swift:368`; it depends on 20 ms sleeps, and that file is also unchanged). `dfa0d5c` under the same load, 7 runs: all passed.

So both failures I saw came under load, in tests that run on this branch's unchanged code; 1-in-13 on the branch, 1-in-7 on the scratch copy of it and 0-in-7 on `dfa0d5c` are too few to say the branch's extra GPU work raises the odds. The mechanism is not shown, and for the map test the likeliest is a pattern already known here: `SharpeningMapTests` shares one float context across tests that run in parallel, the same pattern as `chromatic-aberration/status.md` finding 2 ("Concurrent renders through one float context gave zeros"), which is why `LensRenderingTests` is `.serialized`. The grain test uses a per-test engine, so that does not explain it.

Not a finding against this feature, since nothing in the diff feeds those renders. It should have its own row (the roadmap's existing `ci-test-crash` is the nearest) with the failing values captured, and `.serialized` on `SharpeningMapTests` is a cheap first step. Separately, `status.md` says the two tests "passed on three reruns of those suites"; the coordinator's account has one filtered rerun failing them again, so `status.md` should be corrected to match.
