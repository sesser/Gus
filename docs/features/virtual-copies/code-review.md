# Virtual copies: code review

Owner: code-reviewer. Date: 2026-11-11. Step 4 of `docs/WORKFLOW.md`.
Reviewed: `feature/virtual-copies`, `c72d48e`..`c82e88f` (merge base with `origin/develop`). Build and tests: `swift build` clean; `swift test` 753 tests in 119 suites passed, 1 known issue (the same as the baseline in `status.md`).

## Verdict

Not ready for QA. One blocker: with a sidecar change waiting for review anywhere in the library, selecting an original together with one of its copies (or two copies of one photo) while the Info tab is showing ends the app with a fatal error (C1). The catalog work itself (duplicate, undo and redo, removal, sidecar triggers, pairs, export names) is correct and well tested; C2 and C3 are smaller.

## Questions

Requirements issues for the product manager. Both are behavior the branch has today; neither is in the PRD, the design or the user guide.

- **RI-C1. A copy's Info tab fields write the original's sidecar.** Title, description, copyright and the other descriptive fields are columns of `image`, shared by the original and its copies (`Catalog.setDescriptiveField` maps versions to masters; R8 says export takes "the image's descriptive fields"). Editing one with only a copy selected updates the master, changes what the original shows, fires `sidecar_description` and queues the sidecar. Checked with the scratch executable: rating and keywording the copy left `sidecarQueue` empty; setting Title with only the copy selected queued its master. R7 says "Copies never write or change a sidecar … a copy's changes queue nothing", and AC7 lists only editing, rating and keywording. Options: (a) say so (R7 and AC7 cover adjustments, culling and keywords; descriptive fields belong to the photo and are shared, and the user guide's Copies paragraph and the Copy badge's tooltip say which values are shared); (b) descriptive fields per copy, which needs a migration and is a larger change. The code is consistent with (a); the PRD and the guide need the sentence either way.
- **RI-C2. Keyword suggestions are per master.** `keywordSuggestion` is keyed by `imageId`. Accepting a suggestion on a copy adds the keyword to the copy only (R4 holds) but marks the suggestion accepted for the master, so the original is no longer offered it; dismissing on a copy dismisses for the original too (`Suggestions.swift`, `acceptSuggestion`, `dismissSuggestion`, `setSuggestionState`). Is that acceptable for this feature, or should a suggestion stay open for versions of the master that lack the keyword?

The engineer's own questions stand as written in `status.md` (DQ-V1 to DQ-V6, RI-E1 to RI-E4). DQ-V1 bears on C1: the Changed on Disk source is where an original and its copy are most likely to be selected together while a change is waiting. C1 has to be fixed whatever the ruling on DQ-V1, since any source can hold both.

## Checked and fine

- **Referenced masters.** Duplicate, its undo and redo, and removing a copy touch the catalog only; no file or sidecar path is opened. Offline photos duplicate (tested).
- **Migrations.** None added, none edited; `CatalogSchema.swift` is unchanged. `version` and `editHistory` ids are `AUTOINCREMENT`, so the ids Redo puts back (`restoreCopies`) are never reused by another row in between.
- **Pipeline version and goldens.** No rendering code, cache key or golden changed. A copy shares its original's cache key until edited, which is right: same master, same stack (`previewKeysFollowEachStack`).
- **Edit stacks.** `duplicateVersions` copies the stored text and hash without decoding, so an unreadable stack is copied unchanged and stays protected by `setEditStacks` (tested with a newer schema and damaged JSON). History starts empty; nothing writes over the original's.
- **Sidecar triggers.** v5's `sidecar_culling`, `sidecar_keyword_added`, `sidecar_keyword_removed` and `sidecar_keyword_renamed` all test `isDefault`; inserting, culling, keywording, undoing, restoring and deleting a copy queue nothing, including the cascaded deletes (`copiesNeverReachASidecar` runs the real queue and compares the `.xmp` bytes and `metadataSync`). `sidecarValues` and `applySidecarValues` read and write the default version only. The descriptive-field trigger is RI-C1.
- **RAW+JPEG pairs.** `ImagePairing.partnerVersionIDs` and `setPairsShowCompanion` filter on `isDefault`, so a copy's writes reach no partner and a partner's reach no copy. The grid's pair resolution still reads `imagePair` separately (no join) and indexes only non-copies. `itemCount`, `projectSummaries`, `keywordSummaries` count a copy once.
- **Removal and library-ops R6.** `removalPlan` sorts chosen versions into originals (master, every version, pair partner) and copies that go alone; a chosen copy whose master goes is not counted twice; `extraCopyCount` counts only copies not chosen. `deleteCopies` carries `NOT isDefault` in the SQL itself, so it cannot delete an original whatever it is handed. A copy removed alone leaves `sidecarQueue` and the master. Project removal still takes every version. `removalDidFinish` clears the undo stack for copy-only removals too, so no Duplicate step can redo into a removed master. The one changed existing test (`LibraryRemovalTests.everyVersionOfTheMasterGoes`) follows the PRD's R6, and RI-E2 records the narrowing of library-ops R6.
- **Undo.** The step records the copies it made; Undo captures what the catalog holds for them at that moment (row, keywords, album members with positions, history rows) and Redo puts the same rows back; both run through `persist`. Keywords or albums deleted in between are skipped on restore. The step is registered after the write lands, and the debug script waits for it inside its undo group (`duplicate` is in `changing`; `waitForDuplicate` after every command and after `menukey`).
- **Write chain.** Duplicate is queued on `writes`, so it copies the stack as saved by every earlier edit (edits go through `persist` at once; there is no delayed save). `showCopies` runs inside the queued write, so a reload waiting in `WriteChain.read` cannot interleave with `replaceItems`.
- **Swift 6 concurrency.** Catalog work is in GRDB's async `write`/`read`, off the main actor. `CopyNaming` is a `Sendable` struct of a `@Sendable` closure; `DuplicateStep` is main-actor. No `@unchecked Sendable` or `nonisolated(unsafe)` added. No image work added. (The one main-actor cost is C2.)
- **Export.** Names for the whole batch are still decided by `ExportNaming.plan` before anything is written; a copy's name goes through `ImportTemplate.sanitize` like any other; `{number}`, `{ext}` and import templates still read the file's name (tested). `exportingOriginalAndCopyTogether` compares pixels.
- **UI rules.** No SwiftUI `ScrollView` added. File ▸ Duplicate reads `canDuplicate` from the focused `LibraryMenuState` through `canByKey`; the context menus read the same state. No launch option added. The marks are layer contents made from symbols, as the offline mark is.
- **Branding, strings, clean room.** No brand value outside `AppBranding.swift`; the persisted rule field is `isCopy`. The 17 new keys are in `Localizable.xcstrings` with comments and plural forms (`LocalizationTests`, `BrandingTests` pass). "Virtual copy" appears nowhere in `Sources/` or the user guide.
- **Dependencies.** `Package.swift` unchanged.
- **Tests.** Every criterion AC1–AC9 has a Swift Testing test in `VirtualCopiesTests` that exercises the catalog (no sleeps, in-memory or temporary directories). The app-target glue (`duplicateTargets`, `showCopies`, `hideCopies`, `replaceItems`) has no unit test, as nothing in PhotoApp has; `status.md` lists the debug-script runs, which QA repeats.
- **Security.** No parser of outside files, subprocess, file writing outside the library or network code is added or changed. `/security-review` is not needed for this branch.
